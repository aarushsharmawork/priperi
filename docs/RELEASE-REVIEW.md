# Priperi 2.15.0 production release review

30 October 2026. **Release decision: not yet cleared for public production distribution.** The automated checks below exercise specific boundaries; they cannot guarantee an absence of defects. Production signing, physical-device acceptance and the security limitations below must be resolved or explicitly reflected in the product's claims before release. This review follows the [Android security checklist](https://developer.android.com/privacy-and-security/security-tips) and [OWASP MASVS](https://mas.owasp.org/MASVS/); it is not independent certification.

## Current update: entry flow and prepared signup admission

The launcher is now a cosmetic `SplashActivity`, displaying the existing animated monogram for about240ms (no intentional delay when system animations are disabled). It routes a fresh explicit intent to unexported `MainActivity`, forwarding no caller extras or URLs. Private screens reuse `Ui.loading()` after their existing short delay; cached chats do not acquire a new network wait. Local restoration and login fast paths require matching account/session IDs, closing a possible inconsistent-metadata redirect loop. The server still checks every protected request independently of Activity state.

**Confirmed availability design weakness:** production001–016 has a shared20new-accounts/hour gate. An attacker able to mint claimed device IDs can consume slots; Android ID is not remotely proven hardware. Prepared migration017 replaces that signup charge with server-issued admission after Turnstile verification, before fresh identities consume shared login/signup counters or reserve names. Proofs bind the installation secret hash, installation, scoped ID, username and key fingerprint; used proofs are atomic, single-use and stripped of those binding fields. Expired records are swept. Account deletion clears applicable unused records. Existing accounts, pending idempotent retries and normal sign-in keep their existing protections. Admission is server-only; no Android boolean/header can grant it.

**Activation status: pending, not a live fix.** The hosted project remains001–016 with its deployed relay. No widget, secrets, live migration or relay deployment was changed. Do not apply017 before configuring real provider keys, deploying the complete matching relay and validating genuine provider success on supported physical devices. The new Android client remains compatible with the current server. See [signup deployment](../backend/deployment/SIGNUP-2.15.0.md). New-provider consent/account setup and execution approval are not assumed while the owner is asleep.

Turnstile is an external anti-abuse check: app accounts/messages remain in Supabase, but the provider sees ordinary verification-browser/network metadata. The app never gives its WebView the password, private keys, session or raw device ID; the provider sees an opaque binding. The relay sends the response token and provider secret to a fixed HTTPS endpoint, and checks success, hostname, action, binding and freshness. Verification API output is bounded and rendered only within an origin-restricted native WebView, with no file/content access, mixed content or unsafe Javascript interface. Supabase Free rewrites HTML responses to plain text, so the endpoint returns JSON containing its public template and native rendering explicitly decodes that bounded API response; no custom domain or billing is needed for this design. [Supabase routing constraint](https://supabase.com/docs/guides/functions/http-methods), [Turnstile server checks](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

A human check raises signup automation cost; it does not make the API exclusive to our APK. Human solvers, real-device automation, malicious existing accounts and floods against other public endpoints remain possible. Shared resource ceilings remain, and no large-scale live load test was run. Production signing, sideload-compatible attestation design and capacity planning are still release conditions.

## Retained fixes and policy from2.14.1

The owner considered mandatory QR/NFC/manual comparison excessive. Username discovery now permits the first message without that extra step. Comparison remains available through Chat details → Security key, the QR/NFC contact page and group member details. No automatic verified badge is assigned. A changed pinned fingerprint is still rejected; blocked peers and the three-message introduction limit still apply. A group send still requires active membership and its current server-authorized membership version. Existing single-recipient chat approval remains unchanged. Optional verification does **not** eliminate first-contact directory trust.

The previous profile allowlist, independent encrypted verification map and rejection of file URI document results remain intact. The contact-code confirmation worker also explicitly checks the captured owner before saving trust.

Additional input hardening: `Session.response()` strictly decodes UTF-8, retains the eight-million-byte limit and checks at most32 container levels before invoking JSONObject. `Crypto.verifyProfile()` caps the HPKE public JSON at4096 characters and bounds its nesting before any recursive key parsing. `JsonBounds` handles quoted/escaped braces; the actual JSON parser still checks syntax. Oversized/deep/malformed responses fail as errors instead of entering recursive parsing without a depth bound. This is defensive hardening, not a claim that an ordinary message sender had a reproduced full account exploit. JVM and Android tests exercise extreme nesting, malformed UTF-8, quoted braces and valid responses.

## Confirmed finding — signed ciphertext could jam the inbox


**Fix:** `Crypto.decrypt()` now distinguishes a decryption failure *after* recipient/fingerprint and sender-signature checks from an identity/signature/private-key setup failure. Only that authenticated failure becomes `Crypto.SignedCiphertextInvalid`. Direct and group receive paths durably save an encrypted unreadable placeholder with the original envelope, using the existing authenticated storage/replay machinery, before acknowledging it. A failed local write cannot authorize an acknowledgement. Forged signatures, changed/mismatched identities and unavailable private-key setup still fail closed. Valid plaintext is never fabricated or displayed. This prevents a malformed first page from hiding later valid traffic without treating unauthenticated data as accepted.

**Verification:** `PoisonInboxCase` is called by `NetworkInputTest`. It uses real Android crypto and the isolated HTTP/Auth/SQL fixture, preserves production rate limits, fills the first inbox page through the normal API, and requires the later valid message to arrive and the malformed queue to drain. It also exercises an unreadable signed group copy and verifies that a tampered signature cannot enter the authenticated-placeholder path. No production accounts or live message queues were used.

**Engineering rule:** authenticate first, then isolate unusable input durably so one malicious item cannot monopolize a bounded queue.

## Follow-up: official APK origin is not enforced

A separate follow-up verified this explicitly: the relay has no server-validated app-attestation gate. Seven isolated local assertions passed. A plain Node script could create its own disposable account and submit its own signed opaque envelope without running the Android APK. Missing login and spoofed app/package headers were rejected401; an authenticated token paired with another installation proof was rejected403. This is an absent binary-origin restriction, not a demonstrated authorization bypass into another user's account. Local managed Auth is an explicit test stand-in; the separate real Supabase SDK/JWKS signature test also passed.

Fresh51 bounded live denial probes plus read-only Auth settings passed without creating accounts or making authenticated production writes. No live attack/load test or Supabase log search was performed. Current runtime/source matches the reviewed build. Private evidence: local-only/evidence/app-origin-review.

The owner selected direct APK downloads with public source on GitHub. Production signing remains unconfigured; public source does not remove that requirement. Genuine-app enforcement therefore needs a sideload-compatible attestation policy and a vetted server verifier, not a Play Store licensing requirement. [Play Integrity](https://developer.android.com/google/play/integrity/overview) can provide server-verifiable app/device verdicts; the server must validate recognized app, expected package/certificate/version and [request binding/freshness](https://developer.android.com/google/play/integrity/verdicts). A Play-only licensing policy must not be silently imposed on direct APK users. No attestation was activated during this follow-up. Embedded API secrets, package headers, client-supplied hashes and obfuscation cannot establish official-app origin. Attestation also cannot prevent all automation through real installations or stop arbitrary traffic reaching a public URL; authorization and abuse/resource controls remain necessary.

| APK unpacking, endpoint discovery, public-key extraction | Public configuration is intentionally recoverable. Server authorization never depends on obfuscation. Packaged binaries are scanned for privileged JWTs/server keys/private PEM/service-account JSON/test payloads. |
| Modified APK bypassing login/root/VPN/biometric checks | Private Activities are unexported and account/session gated. More importantly, protected backend operations verify real JWTs, live SQL session, installation secret and actor ownership. Local device restrictions are patchable and do not constitute attestation. |
| Forged/expired/revoked JWT, stolen token alone | Relay validates signature/issuer/audience/expiry and server-managed auth version; SQL rechecks live session and installation proof. Transfer/recovery revokes old installation access. A fully compromised device holding both token and proof remains a threat. |
| BOLA/IDOR, forged sender, cross-user reads/deletes/acks | Server-only SQL binds actor/session/proof to resources and validates membership/ownership. Message signatures bind sender, recipient, fingerprints, ID, time and group context. Attacker tests exercise mismatched actor/proof/recipient and revoked membership. |
| Direct PostgREST/RPC/Realtime/Storage access | Clients have no relay-schema/table/RPC grants. Earlier live catalog evidence found no relay publication/public buckets/client-callable public definers. Fresh bounded HTTP denial probes exercise current hosted endpoints. No service-role key is shipped. |

Messages are native text, not WebView/HTML. Browser links allow only visible HTTP(S), reject custom schemes/credentials/control characters and require confirmation. |
| TLS interception / redirects | Cleartext disabled in normal optimized builds; only system CAs trusted. Untrusted TLS fixture cannot receive the body, redirects cannot forward bearer/body. No trust-all verifier is installed. Pinning is still absent. |

## Conditions preventing an unconditional production clearance

1. **First-contact authenticity remains a known conditional High risk.** Optional comparison restores trust-on-first-use for username-only chats. A compromised directory can supply its own first key; correctly encrypting to that key does not identify the intended person. Pinning catches later changes but cannot validate the original substitution. Users needing this assurance must compare independently. Do not describe username-only messaging as secure against a malicious directory operator.
2. **Forward secrecy remains absent.** Static recipient HPKE permits decryption of captured past ciphertext after theft of that private key. A vetted, versioned ratcheting protocol with reviewed recovery/group semantics and independent assessment is required for a Signal-equivalent claim. The migration plan is in SECURITY-AUDIT.md; no custom ratchet was improvised here.
3. **Actual-device uniqueness is not server proven.** Android ID is only a scoped binding identifier, not a private key or remotely attested hardware identity. A modified client can submit invented identifiers. Shared quotas limit abuse, but cannot prove one physical phone per account. Similarly, local root/VPN/emulator/biometric policies are not remotely unbypassable. Attestation requires a separately designed supported distribution/device policy and backend verification.
The warned fresh-signup path after key loss deliberately accepts the old password plus the matching scoped binding, without the lost private key. It creates a separate identity and never restores old chats; a successful replacement revokes the old session and starts its seven-day inactivity period. A leaked password combined with that binding can therefore authorize destructive replacement. This is a different assurance level from signed transfer/recovery, not proof of possession of the original phone key. The identifier alone cannot authorize it.

4. **Signup/availability capacity needs launch planning.** The currently deployed001–016 shared signup quota is20/hour; prepared017 replaces that particular gate only after verified admission is configured. Additional global continuation/recovery/replacement limits remain. These protect resources but let hostile traffic consume capacity available to legitimate users. Rotating client IDs must not be treated as independent trusted people. A controlled beta fits the current conservative quota better than an unrestricted public launch. Use verified anti-abuse signals and measured capacity planning; simply raising/removing quotas is not a security fix. No live capacity/load/DoS test was performed. The prepared signup policy changes admission rather than simply raising the old quota; it is not deployed.
5. **Production signer/distribution remains unconfigured.** The secure-test APK retains the existing development certificate and `.debug` application ID; the production release is unsigned. Do not publish the development package as the final production product. Owner-controlled signing/Play signing and a migration/distribution plan are needed, especially because identity binding includes package/signing scope. Do not uninstall existing accounts without a verified recovery plan. [Android signing guidance](https://developer.android.com/studio/publish/app-signing).
6. **Physical acceptance remains outstanding.** Real supported biometrics on both phones, account move/rollback/recovery with actual file providers, two-phone NFC/camera, lowest-supported Android and recent Android, OEM notification/background/power behavior and low-storage/process-death conditions need physical testing. The automated screen matrix varies size/font/theme on one Android emulator image; it is not testing every Android version or handset.
7. **Other assurance/privacy limits remain.** System TLS has no managed certificate pin lifecycle; Keystore use does not establish hardware backing on every handset; usernames, group titles, routing metadata and provider retention remain server-visible/linkable. File+24words can decrypt a saved recovery snapshot offline; app password protects server adoption. Zero footprint, total remote erasure and guaranteed absence of vulnerabilities are not achievable claims.

## Evidence and release acceptance procedure

Current run logs and artifacts are listed in VERIFICATION.md. Earlier live catalog results belong to the2.13.0 audit and are retained as dated evidence, not presented as freshly executed SQL in2.14.1. Backend runtime/migrations remain unchanged. Fresh hosted HTTP probes use no owner credentials, valid installation proof or account mutations, and do not search Supabase logs. All destructive/recovery/load tests use isolated local fixtures.

Before approving a public release:

- Confirm the final source/APK hashes, normal BuildConfigs, packaged TLS/backup/export settings and protected component denials. Test only a signed, optimized production candidate for final device acceptance.
- Run the published read-only catalog SQL against the actual deployment after any server change; verify grants, definer search paths, exposures and deployed routine drift. Do not replay old migrations.
- Complete a two-account physical checklist: fresh signup, username-only first message, recipient approval/reverse replies, blocked user, optional correct/wrong QR/key, rename, groups/invite accept/decline/remove, mute/global notification grant/deny, offline delivery, edit/delete/reply, app lock, restart, transfer/rollback, recovery and deletion with disposable accounts.
- Check interruption at each account-move/recovery step: background/rotation/process death/network loss/storage failure/cancel; confirm no wrong-owner content or partial adoption. Confirm revocation from the old phone after completion.
- Establish the production signing/recovery/support process and realistic free-tier capacity/abuse policy. Remove or qualify unsupported anonymity/forward-secrecy/device-assurance claims.
- Obtain independent mobile/backend/protocol review for a public security-focused messenger. Retain an upgrade/incident-response path and monitor dependency/service advisories.

These remaining items are release blockers or product limitations, not checks silently recorded as passed.
