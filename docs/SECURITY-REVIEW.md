## 2.12.0 recovery, notification and file review

The new opt-in kit is a persistent additional authentication capability: file + separate256bit24words + current server-verified human password. AES256-GCM protects its bounded identity capsule; the existing signed authenticated streaming archive protects history/contacts/settings. The original Keystore signing key is not exported. A delegated P256 key in the encrypted kit authorises a new installation signer; account UID/root fingerprint/HPKE identity stay stable. Source sessions are revoked in the same SQL transaction that adopts a collision-checked installation/proof. Repeated same-target completion is idempotent; each new restore still needs a fresh2minute destination-bound nonce and password verification. Revocation/replacement/account erasure/inactivity invalidate access. A completed live move changes the chain and makes the older kit unavailable.

Attacker paths tested: forged recovery key, substituted destination, wrong password, wrong words, modified capsule/archive, stale/replayed nonce, competing challenges, occupied phone binding, expired account, client-role access, malformed nested files and injected transaction failure. Independent committed shared quotas survive proof rotation. The backend does not return managed Auth seeds or verification sessions. Verification sessions are closed after failure/success. Server table stores public delegation/nonce data only; no kit/private key/history is uploaded.53JVM,87backend/5Edge cases and dedicated Android flows pass; precise current counts are in VERIFICATION.md.

A malformed but correctly encrypted file could otherwise exhaust the JSON parser through deep nesting; recovery now uses the same bounded-depth semantic parser as account transfer before adopting any state. Provider copying and frame sizes are bounded. Cancellation clears input/words views; abandoned encrypted cache files are removed at next start/account deletion. Pending import lives encrypted in no-backup app storage and can resume after interruption. External copies cannot be remotely erased. Snapshots can resurrect subsequently deleted local content; users are warned. An old snapshot cannot restore newer chats. A later message-only backup signed by a sibling installation from an earlier reuse may not verify against the new branch; keep a fresh recovery snapshot after a restore rather than relying on cross-branch message-only files.

Mute settings remain encrypted locally. FCM carries only the existing generic inbox hint. It schedules a one-shot OS-owned job before the push callback returns, addressing Android's short callback lifetime without a recurring poller/new library. The job uses the existing coalesced sync budget and account-generation/proof lease; it cannot be externally started. New authenticated content is committed before mute filtering/alerts, and alert emission shares the vault actor with mute writes. Global opt-out, permission denial, foreground activity, wrong account, duplicate receipts and hidden edit/delete controls suppress inappropriate alerts. Muting never blocks delivery.

Static/package/runtime checks supplement source tests; app biometric/root/VPN/screenshot checks are not server hardware attestation and can be patched on a compromised device. Persistent kit custody is an additional risk and is clearly opt-in. Independent cryptographic review and positive two-phone biometric/file-provider/OEM/push validation remain pending. ### Remaining attack paths and limits

A repackaged/root-instrumented APK can bypass local root/VPN/debugger checks and observe plaintext while its owner is using it. Public URL/publishable keys and protocol details are recoverable; backend authorization must carry security. No hardware-backed server attestation or prevention of virtual-device enrollment exists. The install identity/key is not an immutable physical-device identifier.

The same development signing certificate is retained for safe updates; its custody and a production signing/distribution plan remain unresolved. No new production key was generated. Old debug APKs should be replaced. System-CA TLS is used; no certificate pinning is configured. A compromised trusted CA/OS can still intercept, and certificate checks in a patched client can be bypassed. Passing the untrusted-certificate test is not proof against every proxy setup; see [Android TLS configuration](https://developer.android.com/privacy-and-security/security-config) and [OWASP debug controls](https://mas.owasp.org/MASWE-0063/).

A stolen valid bearer token alone still cannot call protected relay actions without the installation proof. It may let an attacker use managed Auth self-service endpoints to disrupt their own compromised account/session. One legacy account still needs correct-password sign-in on its registered phone to complete the existing credential upgrade; its password-only managed-Auth disruption risk remains until then. Revocation cannot retract a request already authorized/in flight. No real owner's password/token was used to probe these paths.

Global quotas bound abuse but also create a shared availability target; this is not a volumetric DoS/load test. Body reads depend on platform request deadlines. Public HPKE key wrapper/algorithm bounds are checked, but the server does not fully parse the inner Tink public-key protobuf; malformed keys can make that account unusable to a sender and fail closed on the client. No custom cryptographic parser was added. Group membership/directory metadata remains server-trusted, without MLS/Double Ratchet/forward secrecy against later long-term-key compromise. Message edit/delete time windows are advisory client-content rules against a modified sender. Deleted messages cannot erase external copies, provider backups/logs or physical flash remnants. Physical OEM/NFC/Drive/battery checks and independent protocol assessment remain pending.

## Remaining limits and release work

- **At the last 2.1.1 hosted check, two existing accounts still required one registered-phone sign-in.** Their legacy managed credentials cannot be transformed without verifying the human password. Until then, someone who knows that password may still disrupt Auth access through its public endpoint. Chat APIs continue to require private proof, and old unbound tokens are rejected. Legacy upgrade is tested locally; existing hosted owners must complete it themselves. Do not claim the migration finished until its count reaches zero.
- **Production signing and physical-phone validation remain.** The installable development APK uses a debug certificate; the optimized release is unsigned. Test multiple physical vendors/versions and permission/OEM behavior before broad distribution.
- **Client checks can be patched.** Root hiding, emulator/VPN/ID spoofing remain possible in a modified APK or compromised OS. Server-verified platform attestation is not configured. Backend authorization remains independent of those heuristics.
- **Static HPKE has no Double Ratchet forward secrecy or post-compromise recovery.** First-contact directory trust remains until fingerprints are compared through a trusted channel. An independent protocol review is warranted for high-risk users.
- **No total footprint erasure.** Provider logs/backups, metadata and contacts' local copies cannot be erased by the app. A dishonest recipient can acknowledge without actually saving. Device ID is scoped and can change after factory reset, signing identity or Android-user changes; ID alone cannot recover lost private keys.
- **Availability and abuse limits remain.** Free-plan global caps can be exhausted for denial of service; client budgets do not replace server limits. FCM, network scheduling and provider cold starts affect latency. The 3.681s fixture measurement is not a production guarantee. Full load, hosted expiry timing and an independent penetration test remain outstanding.
