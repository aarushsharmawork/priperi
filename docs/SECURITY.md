## Account move and inactivity deletion (2.8.0)

Implementation, local tests and the approved production rollout are complete. Existing accounts remain on Never and retain their identities and messages. Live tests verified real managed Auth, transfer/rollback, encrypted capsule transport, queue continuity and deletion of only synthetic accounts. Positive biometrics on two physical phones are still required for device validation.

Both phones use a fresh Android Keystore cryptographic operation gated by BIOMETRIC_STRONG, then require the current app password. A PIN fallback is deliberately absent. Enrollment changes invalidate the biometric key; absent/unsupported biometrics fail closed. UI grants expire after two minutes and on pause. Android receives biometrics; Priperi does not collect biometric templates. This is local owner-consent protection, **not a remote attestation of an unmodified client**. See [Android biometric guidance](https://developer.android.com/identity/sign-in/biometric-auth).

A fresh random256bit secret is encoded with the BIP39 English word list and checksum as24words. The QR contains only those words under a strict Priperi prefix, never a URL. This uses the [BIP39 entropy/checksum format](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki), not its cryptocurrency seed derivation. Words stay local, are hidden on pause and never enter the relay. A domain-separated SHA256 lookup capability locates a15minute one-use ticket. Both the secret and app password are required to derive the capsule AES256-GCM key using PBKDF2-HMAC-SHA256/600,000 rounds, a random salt and authenticated header/lookup. The server stores only bounded encrypted capsule bytes and hashed capabilities. Stealing both words and password can authorise an attacker’s receiver; keep them private. Manual saved copies are not erased by expiry.

The original nonexportable Keystore signing key is never exported. It signs a temporary handoff authority which certifies the receiving phone’s new nonexportable signing key. All certificates bind account/root/parent/child. Chains are canonical P256, bounded at32certificates/16moves and cached only after verification. Only real-device keys at even chain positions may authenticate content; temporary handoff keys may never sign messages, backups, resets or another preparation. Receiver confirmation requires the **current** receiver signer. Historical real-device signatures remain verifiable for saved outboxes/archives. Original HPKE identity/fingerprint and an old local history-index secret move inside the encrypted capsule; API device proof, installation ID and scoped device ID rotate. Contacts pin the original root and independently verify the chain; a failed direct signature refreshes the authenticated peer projection before a second check. Group cache tags reflect updated chains without changing membership. Contacts need2.8 to understand transferred-device signatures. Forward secrecy and post-compromise security are not provided.

A fresh server nonce binds preparation. SQL enforces source proof, recent password, current chain prefix, single receiver, device uniqueness, exact retry digest and expiry under the existing relay transaction lock. Acceptance atomically rotates the device binding, nulls the old FCM token and revokes all Auth sessions; it consumes the encrypted capsule. Durable receiver history import precedes signed finish confirmation. Only then does the source erase local keys/history and acknowledge removal of the private receipt. One consumed private receipt per active account can remain until source acknowledgement, a subsequent move or account deletion; it contains no capsule plaintext/history. An unconfirmed move may return only with original proof/signature, current password and a fresh short-lived rollback nonce. Receiver-confirm/rollback races have one winner. Migration012 removes the abandoned receiver’s installation counters during rollback, preserving unrelated limits. Anonymous pre-login abuse counters retain their existing short expiry; new failed activity can create fresh counters after deletion. The app checks that an abandoned recipient is no longer registered before clearing its local staged copy. It never deletes the other phone’s account. Remote wiping of an offline/modified source cannot be guaranteed.

Full history moves through an optional **offline encrypted file**, separate from the identity capsule. Tink AES256-GCM-HKDF streaming encryption uses a random256bit capsule key; the original device signs the complete stream. Whole-file authentication precedes parsing, with a second verification during transactional import. Bounds are128MiB ciphertext,100,000 records and2MiB per transfer record, with message expansion separately bounded. Metadata is limited to contacts/groups/settings; sessions, server seeds and signing private keys are excluded. Pending outboxes, change/deletion markers and receive digests are preserved and re-encrypted under the new phone’s own storage key. Notifications stay off until enabled there. Android file-picker access is limited to the selected URI; no broad storage or persistent directory grant. Failed/partial exports remain ciphertext. Exported files/provider versions are user-controlled copies.

Inactivity is opt-in1/7/365days or0Never. The server records time, accepts foreground presence at most every five minutes and never renews from background sync/push. Configuration requires recent password and confirmation. The hourly sweep uses the full account erase cascade, including private transfer/capability counters; own login/API/rollback boundaries expire overdue accounts before renewal. A cached deadline gates private content for an online check. Confirmed expiry destroys local keys/data and drops stale local references; signed-out discovery also clears an expired copy after server-confirmed absence. Changing the device clock cannot extend server retention. No unbounded daily scheduler or new wake lock is added. Offline local data, other phones and provider logs/backups cannot be wiped by this mechanism; normal hourly cleanup may lag up to an hour while the service is running, and downtime can delay it further. [Supabase Free projects may be paused after low activity](https://supabase.com/docs/guides/platform/free-project-pausing); paused/offline infrastructure cannot execute cron. Expired accounts are still deleted before renewal when service resumes. No paid upgrade or external keepalive is configured.

## Message changes, replies and optimisation (2.7.0)

A strict versioned binary/base64 content frame is placed **inside** the existing signed HPKE envelope. Ordinary legacy text remains readable; literal reserved-prefix text is escaped as text. Frames have strict UTF-8, type, reference, length and trailing-data checks, a 16KiB decoded cap and a 22,000-character wire cap below the existing relay ciphertext bound. Message encryption, signatures and key pairs are unchanged; no new API endpoint, server privilege, hosted table or permission is introduced. The relay sees the same opaque encrypted messages and enforces the same session/device/signature/block/member/body/queue and rate limits. Controls consume ordinary send/contact allowances; deleting a local message does not restore those allowances. Both endpoints need2.7.0 or later; downgrade is unsupported. Older clients do not understand these frames.

Edit/delete ownership is checked independently of the menu against the authenticated envelope sender and fingerprint, original message ID/time, chat and exact group membership version. Group admins cannot edit someone else’s message. Latest edit order uses signed event time with ID tie-breaking; a valid deletion dominates edits. The app offers editing within15minutes and deletion requests within24hours, using the signed original/event timestamps. These are client content rules, not a new server-authoritative deadline: the opaque relay cannot police the semantic time window of a modified sender. Existing server freshness/expiry/quota rules still apply. A sender controls their own content; no other sender can acquire edit rights by changing a payload target or author claim.

The encrypted local change table uses domain-separated HMAC-SHA256 index tokens under the existing wrapped installation secret; raw author/contact IDs are not index keys. AEAD binds each payload to its token. Per-author target keys prevent an unknown message update from another author preempting its actual author. Applying a valid update and recording its receive digest completes in one FULL SQLite transaction before acknowledgment. Out-of-order updates wait for a matching original, and a mismatched pending update cannot prevent the original from being saved. New unresolved targets are refused when the change-table bound is reached. Authenticated semantic-invalid controls are durably discarded before acknowledgment to avoid repeated processing. Authenticated unsupported/malformed content is saved as a clear placeholder with its original encrypted envelope for possible future decoding, then acknowledged once; it is never executed or rendered as a command. Literal reserved-version text is escaped by the sender. Authentication/storage failures remain unacknowledged. ID/digest conflicts fail closed. Atomic rollback prevents partial updates or deletion after a failed save.

Edited/deleted targets have obsolete ciphertext/signature fields removed locally after transport is no longer pending; encrypted original digests preserve conflict checks. Incoming controls are not history rows. Pending outgoing controls retain the immutable encrypted outbox for reliable retry, then scrub their payload; terminal control rows are pruned after delivery/expiry/group acceptance. Deleting for me writes an encrypted minimal marker, removes cached edit text and prevents an old archive from restoring visible content. A pending message may still be delivered, as stated in the confirmation. Clearing history removes saved rows/edit text caches but preserves deletion/replay markers and pending sends/changes. This is not guaranteed physical-flash erasure or erasure of clipboard contents, provider logs, other clients or backups already saved elsewhere. Account reset/deletion still destroys the complete vault and its keys through the existing path.

Replies carry an encrypted reference ID and current message text, without an embedded copy of the quoted body or author. The receiver resolves a reference only in that chat’s visible local history. Edited references show the latest local text; deleted/missing references show Message unavailable. Reply drafts remain memory-only across rotation. New backups exclude deleted/hidden updates; visible edited/reply metadata is covered by the existing same-phone archive signature and encryption. Restoring an old backup cannot override current deletion markers. Choosing an older archive can restore older text after ordinary Clear history; archives outside the app remain under the user’s control.

Offline dispatch is gated by Android’s existing connectivity permission; callbacks are registered only while a private screen observes sync and removed when it leaves. Reconnection, send and push coalesce under the unchanged24/minute client rolling budget and existing server quotas. Conversation fallback remains4seconds; an idle list uses8seconds after repeated unchanged results, with bounded60second failure backoff. UI observers compare the last displayed per-account vault revision, including changes saved by other worker jobs, to avoid redundant history reads without suppressing real updates. See [ConnectivityManager](https://developer.android.com/reference/android/net/ConnectivityManager).

New databases use incremental auto-vacuum; sufficiently large deletes/clears request bounded page reclamation. Since2.9.1, automatic idle maintenance replaces the Optimise storage action. It uses a60second cooldown and64page reclamation bound. A legacy database converts to incremental reclamation only while idle and charging, with at least32freepages, a16MiB file cap and sufficient temporary disk space; larger legacy files reuse freed pages. Synchronous writes and secure_delete are retained. A conversion rewrites encrypted records, not plaintext staging files, and preserves keys, history and receive digests. Optional incremental maintenance failures do not undo an already-committed deletion. SQLite may need temporary free disk space; actual device battery/storage effects require profiling. See [SQLite auto-vacuum](https://www.sqlite.org/pragma.html#pragma_auto_vacuum) and [VACUUM](https://www.sqlite.org/lang_vacuum.html). No additional wake lock, recurring OS job, device-admin or battery-exemption permission was added.

## NFC contact exchange (2.11.0)

NFC exchanges the same canonical public account UUID and public-key fingerprint as the QR code, never passwords, session tokens, installation proofs, messages or private keys. The contact is resolved through the authenticated relay; UID, recomputed key fingerprint, existing pins and blocks must match. A person must confirm before pinning/opening a chat, with an independent lookup before saving. NFC does not mark the contact verified: the static contact code is replayable and proximity is not proof of private-key possession or a person’s identity. Compare the person you intend to add.

Opening the private contact page arms a90second process-memory public-contact grant for the current account and selected connection. Reader/HCE roles alternate automatically with bounded jitter because Android reader mode suspends HCE. There are no Share/Read buttons. Opening the camera popup revokes the grant; closing it on the still-unlocked private contact page starts a fresh bounded grant. Both devices can exchange the public code through the new APDU; each requires an independent account/key lookup and explicit confirmation. A reader-only phone can pair with an HCE-capable phone; two reader-only phones need QR. Legacy read-only exchange is one-way. Opening the QR scanner, leaving/pausing the screen or a detected unsafe environment revokes it. HCE requires an unlocked, interactive phone, allowed device policy, current session owner and live grant on each command. Process restart has no grant. The exported HCE service is guarded by Android’s signature-level BIND_NFC_SERVICE permission; no NFC Activity, external intent or NFC UID tracking is added. An external reader can receive the public code while you explicitly share; RF relay/eavesdropping/distance cannot be ruled out.

The nonpayment custom AID F05052495045524901 accepts exact SELECT/READ and a bounded public-code EXCHANGE command. It rejects invalid length, nonzero parameters, self/different second peer, expired lease and changed owner. Retrying the same peer does not repeat its callback. Reader mode selects only this AID, with bounded responses, strict canonical parsing, per-command timeout and lifecycle cancellation. It does not interpret URLs or NDEF content or select payment applications. Optional NFC/HCE feature declarations preserve installation on phones without NFC; NFC is a normal install-time permission. No background scan/share is enabled; automatic exchange is confined to the open, unlocked private contact page. Android Beam is not used. See Android [HCE](https://developer.android.com/develop/connectivity/nfc/hce), [NfcAdapter](https://developer.android.com/reference/android/nfc/NfcAdapter) and [HostApduService](https://developer.android.com/reference/android/nfc/cardemulation/HostApduService) documentation. Actual antenna alignment, RF exchange and OEM routing require two physical phones and remain unverified.

## Local message compression (2.5.2)

Only message-record payloads are compressed, separately, before existing Keystore AES-GCM encryption; identity metadata/private keys and network envelopes are unchanged. The existing message-ID AAD and authentication remain. Decryption/authentication completes before decompression. No shared dictionary or plaintext temporary file. See Android [Deflater](https://developer.android.com/reference/java/util/zip/Deflater) and [Inflater](https://developer.android.com/reference/java/util/zip/Inflater) APIs.

Records smaller than1KiB stay in the legacy JSON format. Level1/BEST_SPEED compression is retained only when its full8-byte-header frame saves at least64bytes. The authenticated frame starts PRZ plus version1 and a big-endian expanded size. Both encoded/decoded bounds are1MiB,covering the bounded group outbox. The reader rejects unknown versions,invalid lengths,overflow,truncation,trailing/concatenated streams,dictionaries and invalid zlib checksums. Codec resources close in finally blocks and temporary byte arrays are cleared where practical; this is not a guarantee against memory compromise.

Legacy raw JSON is supported without rewriting existing rows. New/updated rows may require2.5.2 or later to read,so installing an older APK is unsupported. Backup/export still operates on decoded JSON; its format and existing account/key restrictions are unchanged. Compression reduces eligible record bytes,not cloud costs,and does not force SQLite file compaction. Real-device profiling remains pending.

## Groups (2.5.0)

Only accepted members receive new group messages; new members receive no previous history. Each sender creates a separate Tink HPKE ciphertext for every other member and signs it with the existing phone key. The domain `priperi-group-v1` binds group UUID, membership version, message ID, sender, recipient, time and both key fingerprints. The relay verifies every signature and the exact current recipient set under the same transaction lock as membership changes. Existing direct envelopes cannot be relabeled as group messages. See [HPKE context binding](https://www.rfc-editor.org/rfc/rfc9180.html).

This is **encrypted content with service-trusted membership**, not an MLS protocol or an independently audited group protocol. The service stores/authorizes names, invites, membership and admin roles. Known member/contact key changes fail closed, but a compromised membership service can propose new members; compare keys and review group details. No forward-secrecy, post-compromise security or dishonest-sender transcript-consistency guarantee is made. Group names, member usernames/public keys, invitation relationships, timing and copy sizes remain visible to the service.

Admin-only operations are enforced in the service-only database function, independently of UI controls. Invitations require recipient acceptance, cannot be accepted by another account, expire in seven days and reserve bounded group places. Removal/departure invalidates stale sends and purges pending copies involving that member. Exact already-committed retries never recreate acknowledged copies. A changed unsent batch becomes a saved, selectable unsent draft; it is not silently re-encrypted for a new roster. Saved copies already on other phones remain outside remote deletion.

Five group tables have RLS and no client access. The public group RPC is executable only by the existing server role and rechecks live session, device proof, group membership/admin/recipient ownership. Fixed empty search paths and explicit grants follow [Supabase function guidance](https://supabase.com/docs/guides/database/functions). Blocking withdraws pair invitations and removes/suppresses pair copies, while shared group membership metadata remains visible. Account FK cascades erase group references; the oldest remaining member becomes admin when necessary. No new credential, runtime permission or billing service was added.

Storage caps include expired rows until the hourly sweep; a backdated timestamp cannot create uncounted retained rows. Fanout, groups, members, invites, copies, retry markers, body sizes and response sizes are bounded. Names/roles/versions and public keys are included in a roster cache checksum; it only saves repeated downloads and is never used to authenticate access. The group and direct inbox share the existing bounded polling coordinator.

Optional archives include saved group history/public author data only, using the same phone/account-bound signed archive format. Group membership/admin rights, pending fanout and drafts that stopped because the roster changed are excluded. Group history restore requires its existing local group cache and original account keys; it never rejoins a group, grants admin rights or resends an imported message.

## Message and local-data protection

Messages use Tink HPKE with X25519, HKDF-SHA256 and AES-256-GCM. Sender signatures use P-256/SHA256, with the signing private key in Android Keystore. Signature/encryption context binds the message ID, sender, recipient, send time and both public-key fingerprints. Private keysets, installation secret, tokens, contact metadata and message bodies are wrapped/encrypted with AES-256-GCM under a nonexportable Keystore key. Authenticated data separates metadata, individual messages and duplicate-delivery records.

Files live in Android's app-private `noBackupFilesDir`, not a shared storage folder or a root directory. Automatic cloud/device-transfer backups are disabled and excluded. Optional manual archives are described below. Screenshots/recent-task previews are protected with FLAG_SECURE. These are defenses for a normally secured phone; they do not protect against all malware, root compromise, a malicious OS or external cameras.

The construction uses static recipient keys. It does **not** implement Signal Double Ratchet forward secrecy or post-compromise security. Public keys are pinned on first contact and can be compared manually through a trusted channel. A malicious or compromised directory can still target first contact before verification. Do not call this protocol equivalent to WhatsApp or Signal.

Unsent drafts survive rotation only in a memory-held ViewModel. The composer and selectable message text disable saved-instance persistence; plaintext drafts are not written into Android state bundles. Process death discards unsent drafts. Send animation follows the existing durable local save and respects disabled system animations.

## Optional manual message backup (2.4.0)

The user confirms their account password, chooses a separate16–128 character backup password and selects one output document. Android’s [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) supports installed cloud providers, including Drive, without broad storage permissions. The app takes no persistent document/directory grant, collects no Google account identifier and adds no storage permission or paid service. This is a manual file backup; automatic Android backup/transfer stays disabled.

Backups contain saved message records only. Pending outbox entries, login tokens, device proof, private keys, contact permissions and settings are excluded. A random128-bit salt and PBKDF2-HMAC-SHA256 with600,000 iterations derive256-bit input key material; the cost follows [OWASP’s PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Tink AES-256-GCM-HKDF streaming AEAD uses4KB segments and authenticates the version/salt header. See [Tink streaming guidance](https://developers.google.com/tink/encrypt-large-files-or-data-streams). Backup password strength remains important against offline guessing.

An encrypted footer contains a domain-separated ECDSA signature by this phone’s existing nonexportable signing key, covering the complete history stream and owner/fingerprint metadata. Restore first authenticates the entire stream and phone signature before parsing or changing history, then verifies again while merging inside one SQLite transaction. Bad password, truncation, substitution, cancellation or invalid records roll back the import. Existing message IDs are never overwritten; conflicting envelopes fail. Restored outgoing rows are archived, never resent. Current contacts/pinned keys, blocks, approval counters, settings and sessions are retained.

Format bounds:128MiB ciphertext,100,000 records,64KiB per record, strict UTF-8, bounded nesting and fixed KDF parameters. Provider I/O and password derivation run outside the serialized vault worker. Only ciphertext reaches app-private temporary files, which are removed after use/cancellation, on account removal and at next process start. Plaintext records remain in memory and are re-encrypted for local SQLite storage. Password inputs/derived arrays are cleared best effort; no complete RAM-erasure guarantee is made.

**Restore requires the same registered account/root private identity.** After an approved2.8move, the moved identity can verify historical archives; a backup by itself never moves or recovers an account. A backup does not restore login/device keys after uninstall, account reset, factory reset or phone loss. It is useful for recovering cleared saved history while that account/key material remains. Anyone who obtains the backup password can decrypt the archive outside the app; the phone signature protects import authenticity, not secrecy after password compromise. Manual files and provider versions remain in the chosen storage after account deletion until the user removes them. A failed provider write can leave an incomplete encrypted file. Real Drive/OEM/physical-phone validation remains pending.

## First-contact message approval (2.3.0)

A private RLS table stores one directional sender/recipient pair, a saturated1–3 accepted-message count and an approval flag. Existing queued messages/receipts seed that count at upgrade; no account or queued message is deleted. The current migration acquires the shared relay write lock during installation/backfill. Normal sends, approvals, blocks and deletion already use the same transaction lock. Retries with an existing matching message/receipt ID return before charging the contact count. A fourth distinct message is rejected unless one recipient has explicitly accepted the conversation, which opens both send directions from2.12.1. Delivery acknowledgement, receipt expiry, username changes and local chat clearing cannot reset the stored count.

Only the authenticated recipient, with a live session and correct installation proof, can approve an existing incoming request. Client-supplied actor/recipient/approval flags do not control the operation. From2.12.1, explicit approval in either orientation opens both directions of that conversation; it does not override blocks, signatures, key binding, inbox caps or rate limits. QR/fingerprint verification does not itself grant message approval. The new table has no client-role grants; private helper execution is revoked from client/service roles and reached through the existing service-only request function.

The phone budgets pending local messages within the same three slots, retains queued messages while waiting, and resumes them after approved state arrives in the existing bounded sync response. A lost success response still retries the same ID to discover delivery; a rejected queued message is parked until approval so it does not repeatedly consume send calls or block unrelated outbox records. Acknowledgement remains after durable encrypted save. Unchanged state does not rewrite local metadata; approved sends avoid an extra history-decryption pass. Old local history lacking approval tracking does not prevent a new request when no corresponding server history remains.

These pair records persist while the accounts exist because expiry would reset the limit. Account deletion/reset cascades records involving that account in either direction. They contain IDs/count/permission only, without usernames or message text. A new account has a new identity; this feature is not a permanent cross-account/device ban. Free-plan/global abuse limits still apply.

## Contact QR codes (2.2.0)

Contact codes contain only a versioned account UID and public-key fingerprint. They contain no username, device proof, password or token. Renaming does not invalidate a code; the authenticated, rate-limited UID lookup returns the current username. Strict bounded parsing rejects URLs, unknown versions, extra fields and malformed identities before network access. No link or external intent is opened from scanned content.

The relay profile UID, advertised fingerprint and fingerprint recomputed from both public keys must match the code. Self-adds, local blocks and replacement of an existing pinned key are rejected. A confirmation identifies the current username before an independently rechecked profile is pinned and marked verified. Compare the actual person sharing a code; a substituted code from a different account can identify that other account correctly. This is contact discovery, not login or proof of a physical person.

The private, non-exported scanner uses local ZXing decoding. Camera is optional and requested only after Scan a code; denial retains username search and code display. No gallery/storage permission or image upload is added. Camera releases on pause/background/security lock; late callbacks check the active account and lifecycle. Screenshots remain restricted. The library's generic capture activity is removed from the merged manifest. Physical camera/OEM testing remains required. Implementation follows [ZXing embedding/lifecycle guidance](https://github.com/journeyapps/zxing-android-embedded/blob/v4.3.0/EMBEDDING.md).

## Identity and passwords

The account is identified by its registered device proof; returning sign-in requires only a password. A unique editable username is chosen during first setup and used for discovery, rather than account identity. Supabase manages password hashing/sessions using a random internal `UID@accounts.priperi.invalid` alias. No real email or phone number is collected; app tables do not store passwords. Direct managed signup stays disabled.

The app hashes a scoped Android ID into an opaque UUID. Android scopes that underlying ID to the app-signing key, Android user and device; factory reset/signing-key changes can change it. This identifier is not an authentication secret or a guarantee against collision/spoofing. A separate random 256-bit installation secret (only its hash on server) and Keystore signing key protect account ownership. Both installation binding and device-ID uniqueness are checked. Legacy installations retain their private identity and bind the scoped ID after successful password authentication. Lost private keys cannot be recovered using an ID alone.

Forgotten password/username reset requires this phone’s existing private proof and a signature over a single-use, five-minute server challenge bound to account ID, installation and key fingerprint. It deletes the old account rather than revealing/changing its password. The phone stores the reset request encrypted before sending it so an interrupted response can be retried. Local keys/history are erased only after remote deletion is confirmed; a replacement account gets new keys and UID. Contacts’ copies remain outside the app’s deletion control. Android screen-lock confirmation is used for reset when available. If reinstall/clear-data loses the private proof, device ID alone cannot reset the old account.

## Managed Auth binding (current2.8, evolved from2.1.1)

A public internal Auth alias can be inferred from a public user ID. In the earlier implementation, knowing the human password could therefore obtain a managed Auth token directly, outside the relay's device check. The private relay still required the installation proof, so this did not unlock chats, but the Auth API could be used to disrupt sign-in.

2.8 derives the managed Auth credential from the human password and a random **server-only per-account binding seed**, with a domain-separated SHA256 prehash and fixed complexity prefix (68ASCII bytes). Supabase still performs managed password hashing. The private seed is accessible only to service-only RPCs, never profile/directory responses or the APK. The old phone therefore cannot recompute the public Auth credential after a move. API requests separately require the currently registered installation proof and live session. Transfer rotates binding/sessions in one PostgreSQL transaction without a cross-service Auth-password mutation.

New accounts/password changes use version2 immediately. Version0(raw password) and1(installation-derived) accounts upgrade only after correct registered-device proof and successful current-password verification at Continue; version2 never falls back. Protected APIs accept existing bound version1 tokens until normal sign-in upgrades them, but preparing a move requires version2. No owner account is silently reset. The production legacy account still needs its owner’s correct-password sign-in; never describe migration as complete until verified. A stolen managed JWT can still disrupt its own account through Auth self-service; live-session/proof checks independently protect relay data.

## Server authorization and retention

The application tables are in a private schema with RLS and no anon/authenticated grants. Only the server can call the RPCs. Authenticated operations require a signed JWT for this project, a current live Auth session and the correct installation secret. Database transactions serialize relay writes so block/deletion/send races cannot recreate deleted records or bypass a block. Sensitive operations require a password authentication within five minutes. A recent-password prompt is distinguished from an invalid session so reauthentication does not erase the account or incorrectly terminate the password-confirmation flow. Inputs, JSON body size, usernames, public keys, envelopes, signatures and identifiers are bounded and validated. Prepared/RPC parameters are used for SQL.

The receiver verifies and commits incoming plaintext to its encrypted local database, including a duplicate-delivery digest, before acknowledging. The server creates a receipt and removes ciphertext in one transaction. Receipts stop retry resurrection and expire with the original seven-day delivery window. Undelivered ciphertext expires after seven days and is physically swept hourly by the installed hourly pg_cron job. An authenticated dishonest recipient can acknowledge without actually saving; no server can prove the state of someone else's phone.

Deletion atomically removes the Auth user, sessions, profile, blocks involving that user, sent/received queued messages, receipts and attributable counters. A verified recent deletion request can be acknowledged again if the user is already absent, without retaining a deletion tombstone. The phone erases local keys/data only after server confirmation. New activity after deletion, such as failed new login attempts, can create fresh short-lived rate counters.

## Abuse protection and metadata

Rate limits apply to sign-in attempts, installation proof, account creation, search, sync, messages, settings and acknowledgements. Acknowledgements may share one HTTP request (maximum 50 unique message IDs); the server retains the existing per-message quota and recipient/live-session checks for each deletion. The phone includes only messages already committed to encrypted storage. Each acknowledgement is atomic and retries remain idempotent. A recipient queue is capped at 500 messages. The initial anonymous global caps protect the small free deployment but can be exhausted by abuse, causing denial of service. They are not a full DDoS/bot defense. Reassess gateway controls and quotas before opening the app widely; do not silently raise limits or enable paid resources.

TLS protects transport. Hosting/Auth providers can still observe connection metadata, IP addresses, account IDs, timing and ciphertext sizes; the relay sees sender/recipient metadata and public keys. Service logs and database recovery/backups have provider retention outside app-level deletion. The app cannot erase other users' phones or prove deletion of every provider copy. Generic FCM alerts also expose delivery metadata to Google. No message body or sender identity is included in those alerts.


## Device environment and overlays

Normal builds check Android network capabilities for an active VPN, common emulator signals, common root artifacts/test-key systems, and release debugger attachment. Entry, private screens and account/network operations are guarded. Secure windows cover login/settings/chats; normal overlay-hiding permission and obscured-touch filtering protect sensitive taps. Permission HIDE_OVERLAY_WINDOWS is intentional, not access to other apps’ data.

These are local checks, not a claim of unbreakable device integrity. A modified open-source APK or compromised OS can spoof IDs, hide root/VPN/emulator signals or remove these checks. Strong backend enforcement of genuine-device claims requires server-verified platform attestation, which is not configured. VPN use is not inherently illegal; blocking it is this app’s requested policy. Hardware/ROM differences can cause detection gaps or false positives.

The emulator exception is a debug-only build-time QA option. It is never accepted through an intent, preferences or request payload and cannot enable the exception in release. Private QA APKs are kept out of GitHub and shared artifacts. Android secure-window flags do not prevent external cameras or a hostile/rooted OS.

References: [Android ID scope](https://developer.android.com/reference/android/provider/Settings.Secure), [Play Integrity](https://developer.android.com/google/play/integrity/overview).

## Notification consent and delivery

On Android 13+, first launch requests the system notification permission once. Declining still allows setup and messaging; Settings can enable alerts later. On older Android versions the system controls notifications without this runtime prompt. Existing explicit in-app opt-outs are retained. A grant enables registration after a valid sign-in; late token callbacks check the captured account ID before writing. FCM token retrieval runs asynchronously, separate from the serialized vault worker.

One foreground sync coordinator combines screen, send and push triggers. Normal fallback polling waits four seconds after a completed cycle, with error backoff. Push can trigger an immediate sync while a rolling 24-start/minute client budget leaves room below the unchanged server sync quota. Push also triggers encrypted background save followed by acknowledgement, without exposing message text in alerts. These changes do not weaken TLS, message verification, local encryption, device policy or server authorization. Delivery is still best effort and depends on connectivity, platform scheduling and service quotas.
